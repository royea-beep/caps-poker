=== 1 - THE DOUBLE PAINT, REMOVED FIRST AND ON ITS OWN ===

components/Board.tsx: the `background: linear-gradient(165deg, ...)` line inside the
`Platform.OS === 'web'` style block is gone, AND ONLY IT. The absolute-fill <LinearGradient>
child below it survives, because that is the layer native already uses - so this makes web MATCH
native rather than inventing a third behaviour. boxShadow is untouched; it is web's stand-in for
the native elevation and has nothing to do with the panel fill.

WEB vs NATIVE - WHAT IS PROVEN AND WHAT IS NOT. The divergence was WEB vs NATIVE, not
Chromium vs WebKit: the CSS layer lives in the web bundle, so BOTH browsers had it. Measured -
P0 on WebKit reported panelLayers=2, exactly like Chromium. After the fix both report
panelLayers=1, which is the count native has always had (the web branch is false there, so only
the LinearGradient paints).

NATIVE ITSELF IS NOT EXERCISABLE HERE - no simulator, no device, no EAS build in this container.
So "web now matches native" is proven on the web half and inferred on the native half from the
fact that the removed branch never executed on native. Saying otherwise would be the claim this
sprint exists to stop making. A regression guard is committed with it, asserting the SHAPE rather
than the colour: a re-added CSS gradient would restore the divergence without changing a single
token, which a value test cannot see.

Every one of handoffs 108 to 113 said WebKit was unavailable because "its download host closes
the connection in this container". THAT WAS WRONG, and it was wrong in a way I could have caught
at any point: the DOWNLOAD always succeeded. What failed was Playwright's HOST DEPENDENCY check.
`npx playwright install-deps webkit` installs the missing libraries and WebKit 26.4 launches.

So the shipped build is now verified on TWO ENGINES, the first two-engine run since 108:

ONE CAPTURE ARTEFACT, FOUND BY LOOKING AND THEN FIXED. WebKit needs longer than Chromium for the
deal animation to settle: at 4500ms the 393/2P arrangement capture caught the hand tray with 2 of
16 cards dealt, a card-face share of 6.67% against Chromium's 14.37%, where every other cell
agreed within 0.7pp. At 11000ms it reads 13.65% - the same antialiasing gap as everywhere else,
so it was settle time, not a rendering difference. The board panels were fully painted either way
and the panel mask covers only the board area, so no measured number was affected. Settle time is
now configurable.

BROWSER EGRESS TO PRODUCTION IS STILL BLOCKED - retested this session, not assumed:
ERR_CONNECTION_RESET on caps.ftable.co.il. curl reaches it (it goes through the agent proxy, the
browser does not). So both engines run against a LOCAL export of the shipped commit. That is a
real limitation and it is the one that remains after WebKit.
