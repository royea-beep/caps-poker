### ⚠️ ONE REAL FAILURE — `submit_score` MINTS UNLEDGERED. REPRODUCED IN PRODUCTION.

`CLAUDE.md` has carried this as *"STILL OPEN: `submit_score` moves `leaderboard.total_chips` with
NO `chip_transactions` row, so it can break the gap invariant."* It is no longer theoretical.

With a **real anonymous session** — which anyone can mint from the public key in one HTTP call,
proven here: `role: authenticated, is_anonymous: true` — a brand-new device was driven to:

```
total_chips 9,000   ledger_sum 6,000   GAP 3,000   tx_rows 3
```

The 3,000 is exactly the `submit_score` gains, which write no ledger row. Sequence, measured:

- grant on first home call — +2,000, **ledgered**
- `record_reward` ×2 — +2,000, +2,000, **ledgered**, then correctly refused: `reward_cap_daily`, cap 5,000
- `submit_score` ×2 — +2,000, +1,000, **NOT ledgered**, `gain_capped: true` at the same 5,000/day

**Bounded, and the bound holds**: 5,000 chips per device per day, shared across both faucets. But
9,000 is nearly three times the richest real player (3,250), reached without playing a hand.

**Why the live gap is still 0**: `app/results.tsx` calls `submit_score` as an *absolute read-back
write* of the balance the ledger already produced, deliberately sequenced after every ledgered
delta. In normal play it grants nothing. The hole is that the server **clamps** a caller-supplied
number instead of **deriving** it from a verified game event.

✅ The ladder did not move: `elo` stayed 1000 and `games_played` 0 for the forged device. **S2
(server-authoritative ladder) holds** — `hands_played` is writable, the competitive ladder is not.

### ⚠️ `finish_table` — I got this wrong first, and the correction matters

A stranger with no session ended two rooms: `5JT6` and `CZ9Z` both flipped `waiting → finished`,
confirmed by SELECT, on two different forged devices. My first reading was "authorization does not
hold". **Reading the function shows that is wrong in the way that counts:**

```sql
IF NOT v_is_participant AND v_has_fresh_seat THEN RETURN 'not_authorized'; END IF;
```

A stranger is refused **only if a seat was seen in the last 90 seconds**. Both rooms had
`roster_cleared: 0` and `room_players` is empty across the entire database — so what I exercised
was the deliberate **abandoned-room reaper**, not a griefing vector.

The narrower risk that is real: room codes are **four characters**, and the protection lapses
90 seconds after a heartbeat. A tester who backgrounds the app for two minutes can have their
waiting room ended by anyone guessing the code. Nobody has hit it — 0 rooms have ever reached
`playing`. **The branch that protects a live seat could NOT be exercised**: creating a room with a
real seat needs a genuine `users` row, and `create_table` refused the forged host.

Those two rooms are left `finished`. They were empty and abandoned since June; the standing rule
says never hand-edit a `game_rooms` row and it outranks tidiness.

### What a tester will hit, named

1. A room they leave idle for 90 seconds can be ended by anyone who guesses its 4-character code.
2. "Auto-start when full" on two screens, with no other player to fill a table.
3. A wrong URL gives them a developer's "Unmatched Route" page with a Sitemap link.
4. A shop or leaderboard that says "Loading..." indefinitely if their network drops.
5. `/club/DEMO` — any typed code opens a club.
6. Reported previously and unfixed: the achievements filter row clips "Collection"; the reveal's
   DANGER pill reads "ANGER"; the "You won 50 chips!" toast lands on the YOU WIN headline.

### Instrument failures this sprint: SIX

Every one caught by looking at the output, none by a test.

1. `python3 -m http.server` does no SPA rewrite — the first route walk reported **32 of 33 routes
   broken**. A rig defect accusing the product. Replaced with a server that loads
   `dist/vercel.json`'s own rules and reproduces production's honest 404s.
2. I read the card faces as grey from the screenshot. Measured: **exactly #FCFAF3**. My eye, wrong.
3. The tooltip-overlap selector matched a full-page wrapper (393×852) and produced 16 fake overlaps.
4. The first attack batch used wrong RPC parameter names; the 404s looked like refusals. Re-run
   against the real signatures from `pg_proc`.
5. A PATCH returned **HTTP 204** that wrote nothing — success-shaped, and empty.
6. My first `finish_table` verdict — "authorization does not hold" — was wrong in the way that
   matters, corrected by reading the function.

**Yes — CAPS is ready for a tester round on the single-player loop, and only that loop.** The
economy is sound under attack, the ledger invariant holds at 398 devices, every mint vector
without a session refuses, all 33 routes render, and the suite is green at 2,866.

**What I would not want a tester to hit is the multiplayer lobby.** It promises tables that
auto-start on two different screens, no room has ever reached `playing` in the product's history,
and everything about two clients in one room is unverified — so the one surface that has never
worked is the one the copy advertises hardest.

**The single most valuable thing left is deriving `submit_score`'s chip gain server-side instead of
clamping a number the caller supplies** — because it is the only defect proven to break the gap
invariant, that invariant is the alarm every other economic check depends on, and once testers
hold real balances a silent 5,000-a-day drift makes every future economy measurement unreliable.
