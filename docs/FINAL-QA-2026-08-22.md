# FIXED

### 1. ⚠️ The referral feature has never worked for anyone — 3,173 codes, 0 redeemable

`referral_links.referral_code` is generated by a **column default**,
`upper(substring(md5(random()::text) from 1 for 8))` — so **every code the database has ever issued
is 8 characters.** All 3,173, verified from the length distribution: one bucket, `len=8`.

**Every client entry point demanded exactly 6:**

- `/referral` — `maxLength={6}` on the field (so a real code **cannot even be typed**), a Redeem
  button disabled unless `length === 6`, and an *"Enter a 6-character code."* guard
- the **Home** redeem modal — the same three, plus *"6-character code from a friend"*
- `app/invite/[code].tsx` — rejected any code that was not 6, i.e. **it rejected the very links
  `buildInviteUrl()` builds**

Found by trying it: a browser opened `/referral`, was issued `E5DB1AFE`, and the field would not
take it. That zero-redemptions number has been read as *nobody is sharing*. It was **nobody being
able to accept.**

**Fixed** in one shared constant next to the function that embeds the code in the URL. The client is
now deliberately permissive (6–12, normalised to `A–Z0–9`); `redeem_referral` stays the authority and
already answers precisely. Re-deriving the generator's format in the client is what caused this, so
the client no longer tries.

**Proven end-to-end:** `redeem_referral` with a genuine code returned
`{success: true, referrer_earned: 300}`, and the referrer's screen then read **1 friend joined ·
300 chips earned**, on **both engines**.

### 2. ⚠️ The chip store showed no prices at all

With the gate opened in a browser, every pack read **"Buy 2,000💰 for"** with nothing after it, and
the accessible label said **"Buy 2,000 chips for undefined"**. No `$` figure anywhere on the screen.

`app_config` stores **`price_usd`** as a *number*; the screen read **`pkg.price`** as a *string*.
Those names have never agreed. It was invisible because the section is gated, so it would have
surfaced the moment payments were switched on — the worst possible time.

**Fixed at the fetch boundary**, which now converts explicitly **and validates**: a row without an
id, positive chips and a usable price is **dropped** rather than rendered with a hole in it. Display
only — checkout still sends nothing but the package id.

### 3. The referral screen credited 500 where the payout is 300

`/referral` read `app_config.referral_both_get_chips` — **a key that does not exist**. That request
406'd on every visit (the only console error in the sweep) and the 500 fallback always won, so
"Chips earned" rendered `conversions × 500` while `redeem_referral` pays **300**. Two referrals would
have shown 1,000 for 600. Both payouts now live in one pair of constants that render the copy *and*
drive the arithmetic *and* the grant.

### 4. "Restore Purchases" did nothing on web

It called `Alert.alert` directly — a no-op on web, and the **fourth** dead control from this cause.
It sits inside the payment gate, so no player has reached it; it would have shipped already dead,
exactly like the price. The `say()` helper that branches to `window.alert` was trapped inside
`handleBuy`; hoisted, so both paths use it.

### 5. "Coming Soon" → "Payment unavailable"

A promise about timing that depends on an acquirer approving a domain. The per-reason body text was
already honest and is unchanged.

### 6. The QA instrument itself, twice

The ancestor-aware layout classifier, and the self-test that aborts the run if the instrument stops
catching planted defects.

# REPORTED, NOT FIXED

### A. ⚠️ `create_referral_link` mints a NEW code on every single call

The code a player sees changes every time they open the screen. Observed directly: one device was
issued `D17C1EB4` and then `6620B52E` **thirty seconds later**, two rows for one device.

**Root cause, proven not asserted.** The function guards with `IF v_link IS NOT NULL` on a composite
record — which in PL/pgSQL is true only when **every field** is non-null. `user_id` is null on
**3,180 of 3,180 rows** (CAPS is device-anonymous and never sets it), so the branch can never be
taken and the function always INSERTs. That is where 3,173 codes for far fewer devices came from.

**One-line fix: `IF FOUND THEN`.** Not applied — it is a DB function on the referral rail, and the
database has been the strategist's throughout. With §1 fixed the feature now works, but a player who
shares a code today and looks again tomorrow sees a different one.

### B. ⚠️ A tie renders as a defeat

`results.tsx:1327` is a two-branch ternary on `netChips > 0`, so `netChips === 0` falls to the loss
branch. The MP run showed both clients reading **"TIE GAME | 2 — 2"** with **"Defeated by Guest"** /
**"Defeated by Host"** underneath. Both players were told they lost the same tied game. It needs a
third branch. **Winner cue — held per the brief.**

### C. ⚠️ The winning board omits the opponent's hand: *"Straight beats "*

On boards the player **won**, the comparison line ends blank — `"Straight beats "`, `"Two Pair
beats "`. On boards they lost it is correct: `"Full House beats Two Pair"`.

**Multiplayer only — scoped, not assumed.** The same screen in solo is not merely correct, it is
*richer*:

```
solo:  "Two Pair, Jacks and Twos beats Pair of Twos"
       "Full House, Tens over Twos beats Queen-High Flush"
MP:    "Two Pair beats "          <- blank, and the rank detail is gone from both sides
```

So `getComparisonText` is sound (`${p} beats ${b}`) and so is solo's data. In MP the opponent's
**best cards** never reach the winner's client, which both blanks the loser's name and degrades
`getSpecificHandName` to the bare category on the winner's own hand. Result-payload data, not
formatting. **Winner cue — held.**

### D. ⚠️ `/missions` — the same field-name class, plus a reward nothing pays

Reachable **only by typing the URL** (nothing in the app links to it; the Home card was re-pointed
to `/leaderboard` on 2026-07-20). Three defects:

1. the RPC sends `chips`/`xp`, the component reads `chips_reward`/`xp_reward` → every mission renders
   **"0 chips"** and a **blank** XP
2. the RPC sends `completed`/`claimed`, the component reads `is_complete` → `canClaim` is
   `!undefined` = **always true**, so a claimed mission still offers "Claim" and the ✓ badge never
   appears
3. **`claim_mission_d` marks `claimed = TRUE` and returns the chip figure without ever crediting it**
   — verified from the function body, not from the code comment. The client's `+N chips!` toast is
   paid by nothing.

Not fixed deliberately: fixing 1 and 2 would make a screen whose Claim button pays nothing look
*more* finished, and 3 is an economy decision. **Needs a ruling: credit the claim, or retire the
screen.**

### E. Game-screen accessibility — ~27–40 unlabelled focusable cards

Detailed above. Fix shape: an `accessibilityLabel` per card (`"3 of clubs"`), or make them
non-focusable. `Card.tsx` — held.

### F. Performance — the game screen halves the frame rate

~32fps at 320px × 4 boards against 66fps idle on home, and **the reveal is not the cause**. Game
feel — held.
