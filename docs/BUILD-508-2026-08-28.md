## 1. THE STALE TABLE — and it is worse than stale

### 1.1 What I got wrong, and exactly how

Last sprint I reported "the live iOS build is **471**, started 2026-04-27, and builds 460–470 all
failed." I read it from `get_current_build()`. Roye is on 508.

The mechanism is not just staleness — **the reader picks the wrong row even within the stale data**:

```sql
-- get_current_build()
SELECT ... FROM build_history WHERE status = 'live' ORDER BY build_number DESC LIMIT 1
```

It orders by **build_number**, not by date, and **build numbers are not monotonic in time** because
two independent series share the column:

| row | build | profile | date | status |
|---|---|---|---|---|
| newest by DATE | **451** | production | **2026-05-08** | `in_progress` — so `WHERE status='live'` excludes it |
| | 450 | production | 2026-05-08 | `live_on_testflight` — not `'live'`, also excluded |
| | 372 | production | 2026-05-05 | `live` |
| highest by NUMBER | **471** | **testflight** | **2026-04-27** | `live` ← what the RPC returns |

So the RPC returns a row that is **eleven days older** than the newest row in the same table, and
the whole table is **three and a half months** behind the device. Roye's "the newest row is 451,
2026-05-08" and my "471" are both readings of the same table — his by date, mine via the RPC's
ordering. The table's `max(build_number)` is 471; its `max(started_at)` is 2026-05-08. Those are
different rows, and that is the defect.

**It was already written down.** `docs/caps-build-checklist.md:49`, corrected **2026-08-08** —
twenty days before I read it:

> `build_history` | **DEAD.** Last write 2026-05-08; row `451` stuck `in_progress` for three
> months. Do NOT gate anything on it and do NOT write to it.

I queried the table instead of reading the checklist. That is the honest accounting.

**And the same document contradicts itself.** 190 lines later, under "After running checklist":

> Update `build_history`: `UPDATE build_history SET status = 'live' ...`

The 2026-08-08 correction updated the reference table and not the procedure, so an agent following
the checklist is instructed to write to a table the same checklist declares dead.

### 1.4 Why it stopped

**Established: nothing automated ever wrote it.** `grep` across `.github/`, `scripts/` and `tools/`
finds no caller of `register_build` or `update_build_status`, and `git log -S'register_build'` over
all 1,418 commits finds none either. The table was always hand-fed by a person or an agent running
the RPC after a build.

So it did not break — **the practice stopped.** The last write is 2026-05-08; the build pipeline
was replaced twice that month (`ios-testflight-DISABLED.yml` was disabled 2026-05-22, then
`ios-testflight-free.yml`, then the current Expo-free `ios-testflight.yml`), and the manual step
did not survive the migrations. A table that stops being written still answers, which is why it
took three months and a wrong report to notice.

### 1.5 Recoverable? **YES — from CI, not from inference**

**Not backfilled, per the brief, and I did not write to the table.**

Builds 452–508 are recoverable from two sources that were not consulted here beyond confirming
they hold the data:

1. **GitHub Actions** — `ios-testflight.yml` run history carries the commit SHA, timestamp, status
   and conclusion of every run, and `app.json`'s `ios.buildNumber` at that SHA gives the build
   number. Run #1220 (2026-08-06, success) is build 508 by exactly this mapping.
2. **App Store Connect** — the authoritative record of what actually reached TestFlight, including
   builds CI produced but never uploaded. `asc-*.yml` workflows already hold ASC API credentials.

**The gap and cutoff, recorded rather than guessed:**

```
build_history is authoritative:      up to 2026-05-08 (and even then, read it BY DATE, not by build_number)
build_history is silent:             2026-05-09 -> 2026-08-28  (builds 452-508, 57 builds)
the only true source meanwhile:      the installed binary (Settings reads Application.nativeBuildVersion)
```

**Not rebuilt, per the brief.** When Roye wants it: the fix is one step in `ios-testflight.yml`
calling `register_build`/`update_build_status`, so it can never silently stop again — plus
`ORDER BY started_at` in the three readers, a real `LIMIT` in `get_build_changelog`, and a
freshness guard so any reader returning a row older than N days says so instead of answering.
