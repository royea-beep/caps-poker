## Task 1 — where the deal happens today

### 1. Deck and shuffle — **AUTHORITATIVE**, and there is only one of them

| | |
|---|---|
| `utils/deck.ts:3` | `createDeck()` — 52 cards, `${rank}_${suit}` ids |
| `utils/deck.ts:13` | `shuffleDeck()` — Fisher–Yates over **un-seeded `Math.random()`** |
| `utils/deck.ts:40` | `dealCardsMultiplayer(playerCount)` — the real dealer |

**Solo and multiplayer do not differ.** Both reach the same function:

```
solo   app/game.tsx:583  -> initializeGameMulti()  -> gameLogic.ts:187 -> dealCardsMultiplayer()
MP     realtimeMultiplayer.ts:570 -> dealNewHand() -> gameLogic.ts:292 -> dealCardsMultiplayer()
```

`dealCards()` (`deck.ts:81`, the hardcoded 16/16/4-board 2P version) has **no production call
site** — only `gameLogic.ts:32 initializeGame()`, which nothing under `app/` imports, plus
`utils/debug-suite.ts` and tests. Worth deleting during this work, not before.

That single dealer is the best news in this map: **one seam, not two.**

### 2. Distribution — **AUTHORITATIVE**, `utils/deck.ts:51-64`

One index walk over the shuffled deck: `playerCount` hands of `getCardsPerPlayer(n)`, then per board
`slice(idx, idx+3)` open and `slice(idx, idx+2)` closed, remainder discarded. `deck.ts:45-46` reads
`getCardsPerPlayer` / `getBoardCount` — the deduped single source. A duplicate-id guard at
`deck.ts:68-79` re-deals on collision.

**The split is entirely inside this function.** Nothing upstream or downstream decides who gets what.

### 3. Hand evaluation — **AUTHORITATIVE**, and the client is the only judge

| | |
|---|---|
| `utils/gameLogic.ts:326` | `evaluateAllBoards()` → `evaluateOmahaHand()` per seat per board |
| `utils/gameLogic.ts:365` | `calculateChipDeltas()` → the money |
| solo | `app/game.tsx:678` (and a pre-calc at `:438` during the countdown) |
| MP | `utils/realtimeMultiplayer.ts:671-676` — **the HOST evaluates**, then broadcasts `BOARD_REVEAL` / `HAND_COMPLETE`; guests only render what they are told |

Its output is not a display value. It decides the winner, the chip deltas, the COMPLETE bonus, and
what `/results` then reports to the server. **No server code ever recomputes any of it.**

### 4. Bot placement — **AUTHORITATIVE**, one production call site

`utils/botStrategy.ts:156 placeBotCardsWithStrategy()` ← `gameLogic.ts:69 placeSingleBotCards()` ←
**`app/game.tsx:625`**, inside the per-bot timer. It decides the opponent's arrangement, so it is
load-bearing for the result. MP has a smaller cousin: `assignCardsRandomly()`
(`gameLogic.ts:313`) called at `realtimeMultiplayer.ts:660` to fill for a disconnected player.

### 5. Equity and outs — **DISPLAY-ONLY**

`computeSeatEquity` / `computeOuts` are called from exactly one place,
`components/BoardReveal.tsx:191-194`, and their output feeds `EquityBar` and `OutsRow`. Nothing
downstream reads them; the winner comes from `evaluateAllBoards`. **Removing them would change what
the reveal shows and nothing else.**

### 6. What the server is told versus what it decides

| RPC | what the client asserts |
|---|---|
| `record_hand_result_d(p_device_id, p_won, p_boards_won, p_boards_total, p_session_type)` | **who won** |
| `record_hand_net(p_device_id, p_net, p_hand_id)` | **the chip delta** (capped at 20,000/day and idempotent per `p_hand_id` — but the *value* is still the client's) |
| `submit_score` | the stats read-back |
| `update_leaderboard_elo(p_device_id, p_won)` | **who won**, again |

**The server decides nothing about a hand.** It receives assertions and bounds their size. Every
ceiling shipped in the economy work is a limit on how much a false claim can be worth — not a check
that the claim is true. That distinction is what option E changes.

## Task 2 — the seam

### What already exists (checked before proposing anything)

* **11 Edge Functions, none game-related** — bug triage, crash analysis, WhatsApp/Telegram, legal,
  an Anthropic proxy, log shipping. Nothing holds game state.
* **No dealing, shuffling or evaluating RPC exists.** The full room/table surface is
  `create_table`, `join_table`, `leave_table`, `list_public_tables`, `ensure_public_lobby`,
  `finish_table`, `touch_room_player`, `evict_ghost_seats`, `cleanup_expired_rooms`. All seat
  bookkeeping, no cards.
* **`game_rooms` has nowhere to put a deal** — 16 columns, the only jsonb being `game_config`
  (per-room settings). No deck, no hand, no seed.
* **`get_game_config()` already returns all of `app_config` as one object.** Stage 5 (moving the
  balance table server-side for EZ3) should extend this, not add a second config reader. Caution
  while reading it: it returns the *whole* table, including `phase0_channel_authz_enforced`.

### The smallest cut

**The deal itself** — `dealCardsMultiplayer()`. It is one function with one call path per mode, both
already funnelled through a wrapper (`initializeGameMulti` / `dealNewHand`). Replace its body with a
server call and *everything downstream is untouched*: boards, arrangement, reveal, results all
consume the same shapes they do today.

**How each client gets only its own cards — the decision the change turns on.**

A **per-player RPC returning a filtered response**, not a per-player channel:

```
deal_hand(p_room_code, p_device_id) -> { hand_no, your_cards[], boards: [{ open_cards[] }] }
```

* SECURITY DEFINER; first caller for a (room, hand_no) performs the deal and persists it, later
  callers read their own slice. Idempotent per (room, hand_no) — **the same shape `record_hand_net`
  already uses with `p_hand_id`**, so it is a pattern this codebase has already proven.
* **Closed cards are never returned** until a second call at showdown. Today they sit in every
  client's memory from the moment of the deal.
* It **cannot have the current bug**, because there is no player-to-player delivery to authorize.
  Each client asks the server for its own cards over its own HTTPS request. The private-channel
  problem disappears rather than being fixed.

**One new table is unavoidable** — call it `game_hands` (room_id, hand_no, dealt jsonb, created_at),
because `game_rooms` has no column for it. That is the *only* new object; this project's failure
mode is a second half-built thing beside the first, and one table plus one RPC is the whole surface.

**A seed instead of the cards was considered and rejected.** Storing a per-hand seed and
re-deriving needs a deterministic PRNG in SQL (`setseed()` is session-scoped and order-dependent),
and anyone holding the seed can derive *every* seat's hand — so the seed must stay server-side too.
It buys nothing over storing the deal and costs determinism guarantees.

**Solo has no room, and that is a genuine design fork.** Either the same RPC keyed on
`(device_id, client hand id)`, or solo stays client-dealt. The threat models differ — in solo there
is no opponent to cheat — but **EZ3 requires solo to move as well**, because the evaluator and the
bot ship for solo's benefit. Roye's call; the map does not assume one.

**Multiplayer first is not just lowest-risk, it is free**: the thing it would regress is already
broken, and stage 1 doubles as the fix for the P0.

### What must stay client-side

Reveal animation and its timing, card rendering, layout and the fit search, input handling and
selection, hand sorting, Auto-Place, the funnel instrumentation, and the friction signals. None of
them decide anything; all of them are latency-critical.

### Should equity stay local? Yes — with a cost worth naming

It is **display-only**, computed at reveal time from cards the client already holds, so keeping it
local leaks nothing new. It was measured at **119–128 ms** per computation, and the reveal performs
one per board per stage — 8 computations at 4 boards. A round trip is roughly 150–400 ms on mobile,
so the network version is slower *per call* than the whole local computation, and it would put the
reveal animation on the network.

**The cost:** the equity engine is **21,242 of the 35,357 engine bytes — 60%**. Keeping it local
means EZ3 recovers ~14 KB, not ~34.5 KB. Since the mechanic is copyable by watching one hand
anyway, latency is the better trade — but it should be a decision, not a discovery.
