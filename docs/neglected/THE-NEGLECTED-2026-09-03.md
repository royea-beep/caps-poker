## 1 — THE REFERRAL TRUNCATION: fixed, and there were TWO of them

**The bug.** `referral_links.referral_code` is generated by a column default,
`upper(substring(md5(random()::text) from 1 for 8))` — **every code ever issued is 8 characters**
(2,008 of them, all length 8, last issued 2026-09-02, **0 conversions ever**). The manual-entry
field truncated typed input to six with `.slice(0, 6)`. Six characters still *passes*
`isPlausibleReferralCode` (MIN is 6), so the button enabled and a **wrong** code went to the server.

**It survived a previous fix for exactly the reason the brief predicted.** `constants/appLinks.ts`
records the 2026-08-22 pass that widened the validators (`REFERRAL_CODE_MIN 6 / MAX 12`) and fixed
the deep-link route. It missed the slices. So the validation was right and the input still cut.

**Every site checked — read, typed, pasted, parsed, shared, displayed. Six were wrong, in two screens:**

| # | site | was | now |
|---|---|---|---|
| 1 | `app/referral.tsx:249` onChangeText | `.slice(0, 6)` | `normaliseReferralCode(v).slice(0, REFERRAL_CODE_MAX)` |
| 2 | `app/referral.tsx:250` placeholder | `"XXXXXX"` (6) | `"A3F2B1C7"` (8, matching the real format) |
| 3 | `app/referral.tsx:259` a11y label | "…, 6 characters" | "Friend's referral code" |
| 4 | `app/referral.tsx:215` empty display | `'------'` (6) | `'--------'` (8) |
| 5 | **`app/(tabs)/index.tsx:1886`** Home redeem modal onChangeText | `.slice(0, 6)` | same fix — **a SECOND copy of the bug, in a different screen** |
| 6 | `app/(tabs)/index.tsx:1896` visible counter | `{len}/6 characters` | `{len} characters` |

Deliberately **not** hardcoded to 8: `appLinks.ts` warns against re-deriving the generator's format
and drifting a second time. The client stays permissive (6–12); `redeem_referral` is the authority.

**Clean, verified:** `grep` for `slice(0, 6)` / `/6 characters` / `XXXXXX` across both screens returns
only the new explanatory comments. `tsc --noEmit` exit 0.

### Proven by TYPING, character by character
Driven through the real UI with `page.keyboard.type()` — not paste, not a deep link (the deep link
has always worked and proves nothing about this bug).

```

app's own outgoing request:
```

And the server, given exactly that payload, credits the referrer — verified twice, once as
`postgres` and once as **raw anon over HTTP** (the anon path is what the app uses):

```

referral_links.conversions 0 -> 1 ; chip_transactions referral_joined +300
```

**⚠️ HONEST LIMIT — the round trip could not complete inside this container.** The headless browser
cannot reach `supabase.co` at all (`net::ERR_CONNECTION_RESET`, the same egress restriction recorded
in the GO-LIVE-LANDING handoff). So the chain is proven in two halves that meet **at the wire**: the
app emits the full 8-character code, and the server credits on exactly that payload. The one step
not executed in a single process is the packet itself. **A device tap-test is still required** —
it is on the tap list below.

**No backfill.** The 2,008 existing codes were not retro-credited. Every throwaway row

## 3 — THE AUTH GATE: SHIPPED (in this branch), ordering PROVEN, and it needed extending

**Does it still apply?** Yes. `feat/appopen-auth-gate` (`7d44590`, 2026-08-01, one commit) hooks the
gate at `callRPC` in `utils/supabaseEconomy.ts`, and `callRPC` still has exactly the shape the patch
expects. Brought over verbatim: `utils/authGate.ts` + `utils/__tests__/authGate.test.ts`.

**The design is right:** ONE shared in-flight promise (N concurrent app-open effects cost one
sign-in, not N), **bounded at 3000ms** so an auth outage degrades the home screen rather than
blanking it, and placed at the choke point rather than at the three call sites someone happened to
find.

### ⚠️ But as built it was NOT sufficient — four gated functions bypassed it
`callRPC` covers the `supabaseEconomy` family. Cross-referencing the **14** `econ_bind_ok`-gated
functions against every direct `.rpc(` call in the app found four that went around it — including
the two app-open calls MEMORY.md proved race:

| gated function | call site | fixed by |
|---|---|---|
| `claim_daily_streak` | `app/(tabs)/index.tsx:909` | routed through `callRPC` |
| `claim_daily_reward` | `app/(tabs)/index.tsx:746` | routed through `callRPC` |
| `claim_emergency_chips` | `app/gameover.tsx:90` | routed through `callRPC` |
| `update_mission_progress` ×3 | `app/results.tsx:622-624` | routed through `callRPC` |

(The original branch had routed `claim_daily_streak` only, against an older file.) After this,
`grep` finds **no direct call to any `econ_bind_ok`-gated function** anywhere outside
`supabaseEconomy.ts`. `submit_score` is **not** `econ_bind_ok`-gated, so it is not affected.

### Ordering proven on a COLD LAUNCH — measured A/B
Both supabase endpoints intercepted locally and fulfilled (the container cannot reach the real
host). Auth is answered after a deliberate **400ms** delay so a fire-and-forget bootstrap loses the
race; if the economy call still lands second, the gate is genuinely holding it.

| build | first economy call | session ready | verdict |
|---|---|---|---|
| **BEFORE** (`de6af91`, no gate) | `get_poker_shop` @ **1872ms** | 2248ms | ❌ economy beat the session by **376ms**; `get_poker_shop`, `claim_daily_streak` and `claim_daily_reward` all fired session-less |
| **AFTER** (this build) | `get_poker_shop` @ **1554ms** | **1471ms** | ✅ **session precedes the first economy call by 83ms**; all three now land after it |

Non-economy calls (`get_play_of_the_day`, `get_cup_collection`, `get_leaderboard`, `track_event`)
still fire early — correct: the gate holds the economy choke point only, not the whole app open.

**Platforms.** Proven on **web**. **Native was not reachable from this container** and is unproven —
it needs a device run; the shared code path is identical, but that is an argument, not evidence.

**One thing worth fixing next (not done here).** The probe shows **two `signup` requests** (1070ms
and 1134ms): `app/_layout.tsx`'s boot `void ensureAnonymousAuth()` is still a separate path from the
gate. Both resolve and the gate awaits its own, so behaviour is correct, but a launch can mint two
anonymous users. Routing `_layout`'s bootstrap through `ensureSessionBounded()` would collapse it to
one. Small, and out of this sprint's stated scope.

### Can S1 be closed after this? — VERDICT
**Yes, on web, once this build is merged and shipped and field-verified — and NOT before.** With
every `econ_bind_ok`-gated function behind the gate, the ordering that made a server-side
fail-closed unsafe is corrected at the source.

**What would still refuse, and must be handled in the S1 change itself:**
1. **The service-role writer.** `resolve-hand` runs with **no user session by design**. The
   fail-closed rule must bypass on `auth.role() = 'service_role'` **first**, exactly as the CLOSE-S2
   trigger already does, or multiplayer settlement breaks the moment S1 lands.
2. **The 3000ms timeout path.** The gate is deliberately bounded: on a slow or failed auth it
   resolves `null` and the call proceeds session-less. Today that degrades; after S1 it **refuses**.
   That is the correct trade, but it is a real behaviour change and should be measured in the field
   before flipping.
3. **Native, unproven.** Do not flip S1 until the ordering is confirmed on a device.
4. **Anything reaching the economy outside `callRPC` in future.** The choke point holds only while
   new call sites use it — worth a lint rule.

### Remaining path to payments — so Roye can sequence Isracard
1. **Merge + ship this build** (web deploy + a native build). — *this branch, ready now*
2. **Verify the ordering in the field**, native included, on real cold launches. — *needs a device*
3. **Close S1**: `service_role` bypass, then `auth.uid() IS NULL → false`, then
   `WHEN OTHERS → false + log`; re-attack the three mints raw-anon; confirm `resolve-hand` still
   settles. — *one server sprint, branch-first*
4. **Then** enable payments (`iap_enabled`, `web_payments_enabled`) with the receipt path already
   built (`verify-purchase`, `verify_jwt=true`, `credit_purchase` ledgered).

Steps 1, 3 and 4 are each a single focused sprint. **Step 2 is the only one that needs Roye** — a
device and a few cold launches. The letter can proceed in parallel with 1 and 2; payments must not
be enabled before 3.
