# RED-TEAM — attacked from outside, with only what a player has

**2026-08-31.** Everything before this was audit — reading policies, confirming a fix landed. This
was an attack: the shipped public anon key, a browser's `fetch`, and hostile input against all 157
anon-callable RPCs, the Edge Functions, and the payment webhook. **A finding is only real if I
performed it.** Every result below — success and refusal — was a live call against production.

Every attack used attacker-chosen `RT-*` device ids. All of it was cleaned; the gap is back to
**335,330** and no real player's row was written. Attack scripts are in `tests/red-team/`.

---

## ⚠️ SEVERE — found live, and CLOSED during the pass (three of them)

Per the rules of engagement, an actively-exploitable severe hole is closed on sight and said so,
exactly as the ledger was. Three qualified. Each was confirmed by performing it, closed by
migration, and re-attacked to prove the close.

### S1 · `record_reward` — an unlimited chip mint · CLOSED

**Performed:** eight anon calls, no session —
`record_reward('RT-MINT-01', 2000, 'rt_probe_N', false)` — balance climbed **2000 → 16000 →
18000**, one clean 2,000-chip credit per call. Verified twice: nine `chip_transactions` rows,
18,000 chips, by fresh SELECT.

**Why it worked:** `record_reward` is anon-callable and, alone among the anon chip-writers, opened
with only `econ_authz_probe` (which just logs). **No `econ_rate_ok`, no `econ_bind_ok`, no daily
cap.** The amount is caller-supplied, clamped only per-call to 2,000. A loop mints forever. This is
also the referral-reward path, so the referral funnel (`redeem_referral` → `record_reward(300)`)
was unbounded too.

**Closed** (`20260831190000`): added the two missing guards and a 5,000/day per-device ceiling —
the exact posture of `earn_chips`. **Re-attacked:** two grants land (4,000), then `reward_cap_daily`.

### S2 · `submit_score` — a fresh device set to a BILLION chips · CLOSED

**Performed:** one anon call to a device id that did not exist —
`submit_score('RT-BILLION', 'PWNED', 1000000000, 9999, 9999, 999999)` → `total_chips: 1000000000`.
It sat at **leaderboard rank #1** until cleanup. Confirmed twice (a 100k first-call landed 100,000
with `gained_today: 0`, then the billion in full).

**Why it worked:** three guards were added to `submit_score` over time — a +2,000 delta clamp, a
never-lower rule, and a 5,000/day ceiling — and **every one is gated on `v_prev IS NOT NULL`.** They
only run when a row already exists. On the FIRST submit for a device there is no prior row, so all
three are skipped and `p_total_chips` is written verbatim (only the 1e9 absolute cap applies). The
guards fixed the update clobber and left the insert wide open.

**Closed** (`20260831200000`): treat a missing prior balance as 0 so the clamps run on the first
insert too. **Re-attacked:** a fresh device now caps at **2,000**, not a billion. Legit new devices
already have a 2,000 row (starting-grant trigger), so nothing legitimate changes.

### S3 · `evict_ghost_seats` / `finish_wedged_playing_rooms` — a global game-ending DoS · CLOSED

**Performed:** `evict_ghost_seats(999999999)` → `{"ok": true, "evicted": 0}` and
`finish_wedged_playing_rooms(999999999)` → `{"ok": true, "finished": 0}`. The huge argument matches
no rows, so nothing was harmed — but **the calls ran as anon**. Both are `SECURITY DEFINER`.

**Why it's severe:** swap the argument to `0`. `finish_wedged_playing_rooms(0)` sets **every**
`playing` room to `finished` and deletes all their `room_players` — one anon call ends every live
multiplayer hand for every player. `evict_ghost_seats(0)` clears every public waiting lobby. **I did
NOT fire the 0-argument form** — it would damage real and seed rooms; the huge-argument proof
establishes the anon-execute capability without collateral, which is the honest stopping point.

**Closed** (`20260831210000`): revoked anon EXECUTE on both, plus `cleanup_expired_rooms` for
tidiness. They are cron-only — scheduled every minute, and the client's only references to
`evict_ghost_seats` are *comments* about the heartbeat cadence. pg_cron runs them privileged, so the
scheduled path is untouched. **Re-attacked:** all three now return 42501 to anon.

## The three questions Roye asked

### Q1 · Can a stranger mint chips?

| path | result |
|---|---|
| **`record_reward`** | ⚠️ **YES — unlimited. CLOSED (S1).** |
| **`submit_score` first insert** | ⚠️ **YES — a billion on a fresh device. CLOSED (S2).** |
| `record_hand_net` self-reported win | Bounded **by design**: caller reports the net (solo play is self-reported), clamped 10,000/call and **20,000/day**. Performed: hit the 20,000 ceiling exactly. |
| `submit_score` after first row | Bounded: +2,000/submit, **5,000/day**. Performed: hit 5,000 exactly. |
| `spend_chips` negative amount | Refused — `invalid_amount`. |
| `earn_chips` negative amount | Accepted as a **debit** (−500 clamp), not a credit — see Q2. |
| `purchase_item` bogus/negative | Refused — `unknown_item`. |
| `watch_rewarded_ad(random uuid)` | Refused — FK 23503 (user must exist); daily-capped anyway. |
| `claim_mission_d` invented mission | Refused — `not found`. |
| `redeem_starter_offer` as a stranger | Refused — `sign_in_required`. |
| `claim_share_reward` | Bounded: fixed 50, hard **3/day**, needs a real `shared_hands.id`. |
| `claim_emergency_chips(uuid)` | Ledger noise only — keyed on `leaderboard.id`, once/day/uuid, grants nothing playable to an attacker's device. |
| the faucets/rescues (device overloads) | All carry the three guards; refused for a solvent device. |

**Answer: yes, two ways, both now closed.** Everything else is bounded by the daily-cap posture
established in earlier sprints.

### Q2 · Can a stranger read or change another player's data?

**Read — one real leak, performed:**

- ⚠️ **`get_elo_leaderboard` exposes real players' full names paired with auth `user_id` UUIDs.**
  Performed: it returned **"Roye Arguan"** (`d0cc66b9-…`) and **"Avi Avitan"** (`ab1b7383-…`) to the
  public anon key. The ordinary `get_leaderboard` correctly shows only chosen display names and
  **scrubs the device id**; the ELO ladder leaks real identity. **Reported, not changed** — it is a
  read-only PII leak, not a mint or a destroy, and whether the ladder shows names is a product call;
  the `user_id` should simply be dropped from the payload.

**Read — the device id is an unrotatable bearer credential:** `get_home_screen_v3(device_id)` and
`get_player_stats(device_id)` return **any** account's chips, streak, stats and rank to anyone who
passes the id (performed against a known bound device: got its 4,875 chips and full home screen).
This is the designed model, and it is only safe while device ids stay secret. **They do:** the
leaderboard, the ELO ladder, the dashboards and the room listings (`list_open_tables` — the uuids
there are *room* ids, not device ids) leak no device id. So this is not a live break, but it means
**any leaked device id is a full account read + the drain below** — worth stating plainly.

**Change — a griefing primitive, gated on the device-id secret:** `earn_chips` accepts a **negative**
amount (clamped to −500) and the leaderboard update has **no `GREATEST(0, …)` floor** (source), so a
caller who knows a device id can reduce that account's balance 500/call, throttled to 30/min,
potentially below zero. Performed: drove RT-MINT-01 18000 → 13000. **Reported, not fixed** — it is
not exploitable without a device-id leak, and I found none.

**Internal dashboards** (`get_caps_dashboard`, `get_bug_tracker`, `get_analytics_dashboard`, …) are
anon-callable and leak **aggregate business metrics** (player counts, purchase totals) but no PII in
the act. `get_pending_whatsapp_messages` is anon-callable and by construction hands a worker phone
numbers + message bodies — it returned `[]` (nothing queued), so **nothing leaked in the act**; it
should still not be anon-reachable. Weighted low (aggregate/latent, not performed PII beyond the
ELO names).

### Q3 · Can a stranger break the game for others?

- ⚠️ **`finish_wedged_playing_rooms(0)` / `evict_ghost_seats(0)`** — global game DoS. **CLOSED (S3).**
- ⚠️ **`finish_table(room_code)`** — anon-callable with **no authorization**; ends any room by its
  code and deletes its roster. Room codes are 4 chars and are **handed out publicly** by
  `list_open_tables`. **Reported, not fixed:** it is a real client game-action (3 call sites), so a
  blanket revoke breaks the game; it needs a "caller must host/be seated" check — a design change,
  not a one-line close. I could not demonstrate it on a real room without harming a player
  (`create_table` is FK-gated, so I had no room of my own to finish), and I would not finish anyone
  else's.
- ⚠️ **`leave_table(code, ·, device_id)`** — anon-callable, kicks **any** device_id from a room with
  no ownership check. Same class as `finish_table`, same reason reported not fixed.
- `submit_placements` — **well-guarded.** Caller must be seated, and every submitted card must be one
  the server dealt to that exact seat; no forced results, no acting for another seat.
- `cleanup_expired_rooms` — SECURITY INVOKER, already fails closed (42501, anon lacks write on
  `game_rooms`); revoked anyway for tidiness.

### Edge Functions + the payment webhook

- **`verify-purchase` is airtight from outside** — re-proven: no auth header → 401; anon with no
  signature, a forged signature, and a tampered body all → refused; `provider=payplus` →
  `not_implemented`. Nothing credits.
- **`resolve-hand`** (verify_jwt false) validated args (`missing_args`) — no forced result without
  valid game state.
- **`flush-outbound`, `analyze-bug-report`, `retriage-pending`** are reachable with **no key at all**
  and ran (returned `processed: 0` / `messages_sent: 0`). Low severity — operational workers, no
  data returned. One **cost-amplification chain** worth noting: `bug_reports` still has a permissive
  anon INSERT, and `analyze-bug-report` (which calls the AI proxy) is anon-triggerable — an attacker
  could enqueue bug reports and trigger analysis to burn tokens. Cost, not data or chips.

### Rate limits and caps

- The new `record_reward` 5,000/day cap **held under a 12-way parallel race** — total granted 4,000,
  no TOCTOU bypass. `submit_score` (5,000/day) and `record_hand_net` (20,000/day) ceilings held
  exactly under serial fire.
- `econ_rate_ok` is 30/min per device (confirmed in prior sprints; the throttle is per-device, and
  device ids are free, so it bounds a single device, not a determined attacker with many ids — which
  is why the per-call clamps and daily caps, not the throttle, are what actually contain the
  economy).

## Severity, ranked by cost to the product

1. **`submit_score` first-insert → a billion chips** (CLOSED). Highest magnitude: unbounded on any
   fresh device, tops the leaderboard, real spendable balance.
2. **`record_reward` → unlimited mint** (CLOSED). Unbounded via a loop; also unbounded the referral
   funnel.
3. **Global room DoS** `finish_wedged_playing_rooms(0)` (CLOSED). Ends every live game — breaks the
   product for everyone at once, but no economic gain.
4. **`finish_table` / `leave_table` no-auth** (reported). Ends/kicks a *specific* room or player;
   needs a known/guessable room code or device id.
5. **`get_elo_leaderboard` real-name + user_id leak** (reported). Real PII to the public key, but
   read-only and non-compounding.
6. **`earn_chips` negative drain** (reported). Griefing, gated on a device-id secret that does not
   leak.
7. **Anon-triggerable workers / dashboards / cost chain** (reported). Operational and aggregate, no
   PII or chips in the act.

## What I could not test

- **Anything needing a real account:** the `user_id`-keyed paths (`add_xp`, `watch_rewarded_ad`,
  `claim_emergency_chips(uuid)`) are FK-gated to `user_profiles`/`users`, and `create_table`/
  `join_table` need a real host uuid. I could not create accounts, so I could not exercise the
  signed-in economy or a two-real-player MP hand.
- **A native build and two physical devices** — the on-device purchase flow, the real MP
  hand-to-hand, and anything that only manifests in the iOS binary.
- **`finish_table` against a live room** — no safe target existed (I will not finish a real player's
  table), so it is reported from source + the confirmed anon-execute privilege, not performed
  end-to-end.

## Each finding verified twice

Every severe finding was performed, then re-attacked after the close to confirm the fix (record_reward
18k→cap; submit_score billion→2,000; reapers ran→42501). The two read/griefing findings were confirmed
by a live call plus the function source. The refusals are the evidence for everything that held.

## A gap in my own detector, found while cleaning

`v_harness_devices` scans leaderboard, analytics_events, chip_transactions, hand_history,
device_identity, player_streaks and heatmap_events — but **not `referral_links`**. My `RT-REF-OWNER`
device had only a referral_links row and the view missed it. Cleaned by explicit prefix match, which
is more thorough than the view. Worth a line in the detector next time it is touched.
