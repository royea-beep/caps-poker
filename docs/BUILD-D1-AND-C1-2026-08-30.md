### Four widths, two engines — measured, not eyeballed

`tests/home-d1-audit.mjs`, run against the built export:

| width | wordmark | rendered / frame | overflow | clipped | chromium floor | webkit |
|---|---|---|---|---|---|---|
| 320 | 96pt | 239 / 320 = **75%** | no | no | **PASS** | 77%, PASS |
| 375 | 113pt | 283 / 375 = **76%** | no | no | **PASS** | 78%, PASS |
| 393 | 118pt | 296 / 393 = **75%** | no | no | **PASS** | 77%, PASS |
| 430 | 126pt | 317 / 430 = **74%** | no | no | **PASS** | 76%, PASS |

Playfair Display resolved on both engines at all four widths. WebKit sets it 1–2 points wider
than Chromium, which is why the ceiling matters: at 430 the cap holds it to 126pt rather than
letting `W × 0.30` reach 129.

**The overflow risk was real and is why this is a table rather than a sentence.** Four capitals
at a serif's ~0.72em advance is ~2.9em; 0.30 × 320 × 2.9 = 278pt inside a 320pt frame. That is
tight, and `adjustsFontSizeToFit` — which rescues native — **is a no-op on web**, a fact this
project learned from the REMATCH regression. So it is measured at every width on both engines.

### ⚠️ Two things the concept render could not tell you

Both are properties of the app, not of the choice, and neither changes it.

1. **Playfair Display does not exist on native.** There are zero font files in `assets/` and
   `expo-font` is never imported — the same fact `Card.tsx` already records as *FONT RULING A*
   for `CARD_BACK_FONT`. The render Roye approved is set in Playfair; **on a phone it cannot
   be**, because the font is not in the binary. `default: undefined` used to resolve to the
   system *sans*, which for a masthead is the wrong shape entirely, so the fallbacks now name
   serifs that are actually present: **Georgia on iOS** (bundled, genuinely high-contrast),
   `serif` on Android (Noto Serif), Playfair on web. That is asset-free and follows the existing
   precedent instead of inventing one — when a font-infra batch bundles Playfair, this single
   constant changes and all three platforms match.
2. **The gold gradient is web-only.** `webTitleGradient` uses `background-clip: text`, which
   React Native has no equivalent for. Gradient-filled text on native needs
   `@react-native-masked-view/masked-view`, which is **not installed** and which I was told not
   to install. On native the wordmark is therefore **solid `#c9a84c`**. Nothing was changed to
   make this so — it is the behaviour the existing `isWeb &&` guard already had; it simply
   mattered less when the word was 41pt.

**Net:** web gets the render. iOS gets a solid-gold Georgia masthead at the same size and
position. Whether that gap is worth closing is a font-infra decision, not a D1 decision, and the
one-line hook for it is already in place.

### Gold semantics — my view: it does not dilute, and here is why

The WON cue is `components/Card.tsx:475` — `borderWidth: 3, borderColor: '#FFD700'`. Measured:

| | value | luminance | on the page ground |
|---|---|---|---|
| WON cue | `#FFD700` | 0.699 | 14.12 : 1 |
| D1 wordmark | `#c9a84c` | 0.409 | 8.66 : 1 |

**They are 1.63 : 1 apart in luminance — not the same gold, and never were.** Four reasons the
enlargement is safe:

1. **D1 introduces no new gold.** `theme.titleColor` has been `#c9a84c` since the theme existed;
   the wordmark was already gold at 41pt. D1 changes the *size*, not the *category*.
2. **Different swatch** — the table above.
3. **Different medium.** WON is a 3px border plus a glow on a *card*. The wordmark is *type*.
   A player never has to decide whether a letterform is a winning border.
4. **They never co-occur.** The wordmark lives only on Home; the WON cue only on a board and in
   results. There is no screen where both are visible.

The closer neighbour is the **daily-bonus pill**, which is gold *and* a reward cue *and* sits on
the same screen as the wordmark. That is pre-existing and I have not touched it.

**No change proposed, because none is needed.** If Roye wants the separation guaranteed rather
than merely true today, the smallest possible guard — and it keeps his choice completely intact —
is to give the two golds named constants so the wordmark can never drift to `#FFD700` by a future
edit. That is a refactor with no visual effect, so I have not shipped it unasked.

### The floor, and the instrument that proved itself first

**PASS at all four widths on both engines**: 0 contrast failures, 0 controls under 44pt, 0
unnamed controls, 0 page errors.

Every run ends with a **planted canary** — `#2a2a2a` on `#0a0a0a` (~1.4 : 1, must fail) beside
`#f0ead6` on the same ground (must pass). All eight runs: canary OK. Had it not been, the run
marks itself `VOID` and no number in it is quotable.

> **The canary immediately caught itself.** Its first version injected the two spans into the
> audited page — where the ground-shot style tag (`* { color: transparent !important }`) was
> still in force. Both canaries rendered invisible, both scored an identical **1.06**, and the
> *good* one failed for the same wrong reason as the bad one. It now runs on a blank page and
> takes its own ground shot, which is the only way it tests the real scoring path. That is the
> fourth instrument in this series caught by this discipline.

**One pre-existing defect fixed, found by that verification** — `components/SideMenu.tsx:108`.
The backdrop was the single unnamed control on the home screen, on the *shipped* build as well as
the new one, and it had two faults: no accessible name, and **still focusable when closed**.
SideMenu stays mounted with `pointerEvents: 'none'`, which stops touch but does not remove an
element from the tab order or the accessibility tree on web — so a keyboard or screen-reader user
landed on an invisible 393×788 target on every screen that renders the menu. `focusable={visible}`
is the part that fixes it; `pointerEvents` was never going to.

## 2 · C1 — the icon, redrawn for the square

**A cropped hero is not an icon** — my own sheet said so. What changed from the hero:

| hero | icon |
|---|---|
| rotated −4° | **upright** — a tilt reads as craft at 1024 and as a mistake at 60 |
| floats in a tall portrait frame | **composed for the square**, centred |
| no safe-area allowance | **sized from the mask**, separately per platform |
| rank glyphs in the corners | **none** — at 60px a corner "A" is three pixels of mud, and C1's measured strength was being *one clean shape* |
| — | **a gold `#c9a84c` hairline**, D1's own value: what makes these two roles of one identity |

**The sizes are derived, not chosen by eye.** iOS masks a superellipse; Android may mask to a
circle of 66% diameter. The card is taller than it is wide (0.70), so the binding constraint is
its **diagonal**: half-diagonal = `f × √(0.25 + (1/0.7)²/4)` = `f × 0.8719`, so fitting a 0.33
radius needs `f ≤ 0.3785`. The Android foreground uses **0.36**; iOS uses **0.56**, which gives
0.80 frame height and a real 10% margin top and bottom.

> **The first attempt got this wrong and the sheet caught it.** The foreground was drawn at 0.40
> with a comment claiming it cleared the mask. It did not — the approval sheet's dashed 66% ring
> showed the card's corners poking out. The fraction is now computed from the geometry, and the
> ring in the sheet is there so the claim can be checked against the picture rather than believed.

### 60px legibility — measured, like for like

| | subject % | contrast | regions ≥1% | crispness |
|---|---|---|---|---|
| **the designed icon** | **41.4** | **18.96 : 1** | **1** | 0.470 |
| C1 hero, cropped | 48.8 | 18.73 : 1 | 1 | 0.557 |
| I1 (the one it beat) | 34.5 | 8.71 : 1 | 1 | 0.155 |

The designed icon is *deliberately smaller* than the crop: the crop had no safe margin and would
have been shaved by both masks. It keeps the two properties that decided C1 — highest contrast
and **one region** — and it still comfortably beats I1 on every axis.

### What the icon needs to ship

**Nothing in config.** `app.json` already points at every path written, so there is no
configuration change and no new key:

| asset | size | role |
|---|---|---|
| `assets/icon.png` | 1024² | iOS + general |
| `assets/adaptive-icon.png` | 1024² | legacy Android key, kept in step |
| `assets/android-icon-foreground.png` | 1024², alpha | card only, inside the 66% circle |
| `assets/android-icon-background.png` | 1024² | the ground |

## 4 · Delivery — `cmd.exe`, byte-safe

PowerShell's `>` re-encodes and corrupts PNGs. Use `cmd.exe`.

```
cd /d C:\Projects\POKER\Caps
git fetch origin claude/vamos-caps-align-celebration-flppo0
set R=origin/claude/vamos-caps-align-celebration-flppo0
git show %R%:docs/d1-home/_approval-sheet.png > "%USERPROFILE%\Downloads\_approval-sheet.png"
git show %R%:assets/icon.png                  > "%USERPROFILE%\Downloads\caps-icon-1024.png"
dir "%USERPROFILE%\Downloads\_approval-sheet.png" "%USERPROFILE%\Downloads\caps-icon-1024.png"
```

Individual widths are `docs/d1-home/home-d1-320-chromium.png` and the 375 / 393 / 430 siblings
(and `-webkit`). Verify by size — a much **larger** file means it was re-encoded and is broken.
